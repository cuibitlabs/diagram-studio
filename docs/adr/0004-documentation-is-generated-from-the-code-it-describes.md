# 4. Documentation is generated from the code it describes

**Status:** accepted

## Context

Per-type reference documentation is where diagram systems rot. There are 31 types; each has a default direction, a set of model fields it reads, starter content, and a size. All of that changes as the renderers change, and hand-written docs describing it are wrong within a release. Nobody notices, because nobody diffs a document against a renderer.

## Decision

`skills/create-editorial-diagrams/references/type-*.md` is generated by `scripts/build-type-docs.mjs` from three sources:

1. the type registry (label, family, description, direction),
2. `src/types/guidance.js` — the editorial judgement a renderer cannot encode: when the form is right, when it is wrong, its composition rules, and the mistake people make with it,
3. the type's own starter content, rendered to get real dimensions, the fields it actually reads, its `.ds` source and its Mermaid equivalent.

`scripts/verify-docs-sync.mjs` regenerates each doc in memory and fails the build if what is on disk differs, if a type has no guidance, or if the skill and README's headline numbers no longer match the registry.

## Consequences

- Editing a generated file is pointless; the header says so and CI enforces it. Guidance is edited in `guidance.js`, next to the code.
- Adding a type without guidance fails the build, which is the intended pressure: a type nobody can explain when to use should not ship.
- The prose that matters — the judgement — is still written by hand. Only the facts are generated.
